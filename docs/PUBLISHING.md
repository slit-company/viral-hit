# Publishing implementation status

YouTube transport, a connector, a durable SQLite publication store, a single-step worker and retained project-media storage exist under `core/publishing/`. They are not connected to a publishing UI, HTTP/MCP command or background scheduling loop yet. No real account upload has been performed. Meta/Instagram remain pending. A generation receipt or local export is not a published post.

The transport verifies the OAuth channel, then uses the same credential to create a resumable session. Privacy, audience, synthetic-content disclosure and subscriber notifications are explicit. Scheduled time is checked again after account discovery. It accepts only the expected HTTPS Google upload endpoint and sends fixed 8 MiB chunks (except the final chunk), with provider-reported offsets. Session probes can recover the original video receipt after a missing final acknowledgement. Expiration and unknown outcomes never automatically create another session. Upload acceptance, processing and privacy remain distinct fields.

The implementation follows Google's [resumable-upload protocol](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol), [video insertion contract](https://developers.google.com/youtube/data/reference/rest/v3/videos/insert), [video metadata/status contract](https://developers.google.com/youtube/data/reference/rest/v3/videos) and [channel identity lookup](https://developers.google.com/youtube/data/reference/rest/v3/channels/list). Reads have bounded JSON bodies; fetches have a 30-second deadline and redirects disabled. Credentials/session URLs are not included in diagnostic errors.

The generic intent binds account, destination, connector version, asset hash/size and metadata to one approved digest/revision. Edits invalidate approval. A stable request key prevents duplicate intent creation. Session URLs and raw connector receipts are excluded from its browser projection. The worker persists `starting` before creating a session and persists the returned checkpoint in a separate commit before transmitting media. A crashed `starting` action stays uncertain. Known sessions recover from provider-reported progress, and accepted receipts can be inspected after source media is removed.

Local stop prevents subsequent local work; it does not delete an uploaded video or cancel a remote schedule. The old lease deadline remains a quarantine for in-flight requests, so immediate reconciliation cannot race a previous writer. Reconciliation queries the original remote identity; continuing an incomplete upload requires a separate resume. An unknown creation without a stored identity cannot automatically be retried. Runtime/credential resolution remains a server boundary that must honor cancellation. The project-media implementation now resolves actual local project memberships, retains verified bytes and supplies bounded integrity-checked ranges to the executor.

No dependencies or browser modules were added. Media transmission uses fixed 8 MiB chunks and one bounded action per lease. Store JSON is limited to 128 KB per value; repeated unchanged polls update the existing row rather than append idle events. [Project-media retention](PUBLICATION-MEDIA.md) streams full-hash verification during preparation, stores indexed block hashes and checks only the blocks touched by a later read. Source edits/deletion cannot replace approved bytes. Large synthetic-file measurements are recorded in [performance](PERFORMANCE.md); they are not live upload benchmarks.

The 41 publishing tests cover metadata/scheduling, credential consistency, project/revision boundaries, redaction, lease fencing, recovery, phase separation, wrong/ambiguous channels, hostile URLs, invalid ranges/chunks, expired sessions, bounded responses, and partial/final response loss. Media coverage adds real project image/audio/video retention, foreign membership, deleted projects, changed source content, unaligned ranges, corruption, symlinks, cancellation, concurrent preparation, orphan recovery and missing integrity records. A project integration sends the retained bytes of a real FFmpeg-generated video through the YouTube connector's fetch fixture after deleting the source; its received SHA-256 matches the approved pin.

The local HTTP transport test transmits actual bytes, deliberately loses acknowledgements, resumes one session and verifies SHA-256. A separate connector/executor test reopens a real SQLite database between steps and reproduces partial/final acknowledgement loss through a fetch fixture with exactly one session creation. These do not establish Google acceptance, OAuth readiness, channel permissions, quota availability or real public visibility.

Before exposing publishing, complete the [application boundary](architecture/003-publishing-intents.md): account connection/credential isolation, safe provider-specific receipt projection, worker scheduling, shared UI/HTTP/MCP operations and an authorized live test. Retained-media lifecycle and cleanup also remain to be defined. reference pipeline's separate staging/publication/recording stages inform this boundary; its brand-specific account data and policies are not copied.
