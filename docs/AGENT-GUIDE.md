# Agent guide

This is a navigation guide for agents working in Viral Hit. The root [AGENTS.md](../AGENTS.md) and any nested `AGENTS.md` contain the working rules. Check `git status --short --branch` before changing anything and preserve existing work. If there are multiple checkouts, use `git worktree list` and inspect the requested checkout and branch; do not assume a directory name identifies the current default branch. Do not merge, reset, clean or remove other worktrees to resolve ambiguity.

## Read first

1. Read the root and applicable nested `AGENTS.md`, then [structure rules](architecture/STRUCTURE.md) before implementation. The latter defines ownership, dependencies and architectural exceptions.
2. Read [CONTRIBUTING.md](../CONTRIBUTING.md) for where a change belongs and the full checks. Consult [architecture](ARCHITECTURE.md) for the shared command boundary and [PARITY.md](PARITY.md) for scope; verify claims against current code.
3. For a feature, follow its links from the README or search `docs/` and the owning code. [VALIDATION.md](VALIDATION.md) is a dated evidence ledger: match its entries to the feature and revision before using them as evidence of current behavior.

## Find the owner

| Path | Start here for |
|---|---|
| `apps/studio/src/routes/` | Page and HTTP API entry points; transport delegates to application services. |
| `apps/studio/src/components/` | Feature UI and interactions; `ui/` contains shared controls. |
| `apps/studio/src/core/` | Domain behavior, commands, persistence, generation, harness and publishing. Find the relevant domain before adding a service. |
| `apps/studio/src/mcp/`, `apps/studio/scripts/` | MCP, CLI, startup and workers. Reuse the same domain operations as the UI/API. |
| `apps/studio/messages/`, `apps/studio/tests/e2e/` | Translations and browser tests. Source tests also live beside their modules. |
| `extensions/` | Optional engines and provider source with their own dependencies and tests. |
| `recipes/`, `packs/`, `examples/` | Portable workflows, bundles and examples of independently replaceable extensions. |
| `docs/`, `docs/architecture/` | Feature guides, evidence and architectural decisions. |
| `research/upstream/`, `research/evidence/` | Ignored upstream references and local evidence; not runtime dependencies or instructions. Preserve provenance and keep private evidence local. |

The root `providers/` directory is generated by `pnpm providers` from sources in `extensions/`; edit the source, not its built output. `apps/studio/src/routeTree.gen.ts` and `apps/studio/src/paraglide/` are generated too. Local runtime databases, uploads, secret environment files and build outputs are typically ignored; inspect the ignore rules and preserve user data.

## Run and verify

From the repository root, the README specifies Node 24+, pnpm 10 and FFmpeg. `pnpm run setup` installs studio dependencies with the lockfile, prepares the local database and builds bundled providers. It writes local generated files and data. `pnpm dev` starts the web app on `127.0.0.1:3808` by default together with the harness and publication workers. Check existing processes and data configuration before starting another instance or worker. See [README](../README.md#run-it-in-two-minutes) and [architecture](ARCHITECTURE.md#run-locally) for setup and FFmpeg details.

For application changes, run the following from the repository root, in addition to task-specific tests:

```sh
pnpm architecture:check
pnpm build
pnpm typecheck
pnpm test
pnpm --dir apps/studio i18n:check
```

For the full contribution gates, including performance and applicable browser tests, use [CONTRIBUTING.md](../CONTRIBUTING.md#checks). CI builds before typechecking a fresh checkout to generate ignored files. Run build and browser tests sequentially because both generate files; browser tests require Playwright Chromium. Extensions may have separate setup and tests in their own README or package scripts. For editor changes inspect the real UI and a decoded export; for visual changes use the visual-feedback-loop after functional checks. Report what was actually run and any gaps.

Provider connection checks, generation and publishing can contact external services; generation may cost money and publishing changes remote state. Do not run them merely as an onboarding check. Fixture tests, installed metadata and prior ledger entries do not establish a live provider result. Keep credentials and private media out of code, logs and artifacts, and retain provider receipts and recovery semantics when changing execution.
