# 008: Publication admission and execution

The publishing application service owns project, connected account and retained-media admission. HTTP, MCP and CLI accept a project asset ID, a workspace account ID and connector metadata. They cannot choose a filesystem path, content hash, remote session or destination identity. The service derives these from the current project and verified account, retains the original bytes, and returns an explicit public projection.

Each creation request has a durable admission digest alongside the existing original specification digest. Replaying the same request returns its current publication even after a revision or removal of the source file. A different request under the same key conflicts. Existing database rows migrate with an unknown admission digest and cannot silently acquire a new admission identity. Approval binds the displayed revision and specification digest, requires explicit confirmation, and verifies retained media, account and runtime configuration. Editing invalidates approval.

The publication worker is a separate process from generation. It uses the encrypted account service and retained-media reader, checks the active project and original destination, and executes one bounded action per lease. Unconfigured accounts cause local backoff without remote submission. The existing worker commits `starting` before session creation, commits the original session before sending bytes, and preserves uncertainty after an ambiguous response. A stop fences the writer but retains its lease quarantine. Reconciliation probes the original session without sending video bytes; continuing an incomplete upload requires explicit confirmation.

Shutdown aborts the current request and awaits the step before closing stores. HTTP mutations enforce the workspace header, origin checks, bounded JSON and strict schemas. Read responses use the same browser trust check. Public views exclude credentials, sessions, leases and arbitrary provider responses. Remote status remains an observation, not proof of a later state. These controls support an operator-controlled workspace; they do not add multi-user authentication.

Verification uses real project assets, encrypted account storage, migration/replay tests, real worker steps and fixture network transport. No fixture establishes live Google consent or a real published video.

The review page previews retained media, not a mutable original URL. The media read binds the project/publication/digest, checks the active project and connector, and verifies each bounded byte range through the shared retained reader. Native video requests cannot attach the workspace header, so this read rejects foreign Origin/Fetch-Metadata and sets same-origin CORP, no-store and nosniff. Every opened media store closes after its read; cancellation aborts pending reads. A revision changes the digest and invalidates an older preview URL.

TanStack Start treats native media destinations as static requests before file routes. The existing shared dev/production normalization now includes only the exact retained-publication media path in addition to project assets. It removes `Sec-Fetch-Dest`, preserving Fetch-Site, Origin, Range and digest checks. Browser playback and a cross-site media request verify both dispatch and trust enforcement; calling the handler directly cannot establish this framework boundary.
