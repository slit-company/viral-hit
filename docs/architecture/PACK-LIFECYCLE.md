# Recipe pack lifecycle

Recipe packs use the harness recipe library, including its existing SQLite transaction boundary. Updates keep a pack ID and change its declared composition. Review shows the complete incoming definitions beside every current affected definition. Missing incoming recipes are added; differing existing recipes are kept unless explicitly selected for replacement. Recipes dropped by a release stay installed independently. Removing a pack keeps recipes by default; explicit deletion is limited to present members not referenced by another pack or the file catalog.

A review digest binds the pack summary, installation identity, current definitions (including absence), file-catalog reservations and memberships of every affected recipe. Mutation recomputes this snapshot under `BEGIN IMMEDIATE` and rejects stale reviews before writing anything. Pack metadata and recipe changes commit together. No network access, job changes or project changes occur in the transaction. A repeated stale update is rejected; clients reload to reconcile an unknown outcome rather than resubmit different content. Removal of an already absent pack is a no-op and never deletes detached recipes.

The existing summary is enough to project complete/modified/missing content; no revision archive or new dependency is added. A user can retain local recipes while adopting new metadata, so the resulting pack can correctly show modified content. HTTP, MCP and CLI call the same service. Bundled offerings remain file-managed; their installed copies use this lifecycle. Creative packs retain immutable export snapshots and are a separate composition boundary; runtime extension lifecycle is also separate.

Verification must cover stale and concurrent mutation, selective replacement, preserved dropped/shared recipes, reserved IDs, rollback on library limits, incomplete packs, saved jobs and transport trust.
