# 014 — Portable editable sequences

A generic `editor.sequence` harness step prepares a versioned edit intent using pinned project assets. The pure contract belongs to `core/editor/sequence.ts`; preparation, materializer bindings and receipts belong to the harness. It neither renders nor changes the timeline. Recipes and independent planners can author the same sequence without importing app internals or using a particular generation engine.

Sources are named project asset IDs and media kinds. Admission pins project, asset ID, kind, content hash and size. Upstream bindings accept only a declared same-kind materializer dependency's asset ID and automatically bind its complete identity. Clip fields can consume other dependency outputs; asset metadata and pins cannot. Execution and acceptance validate all present originals again and probe a private copy of the verified bytes. Source ranges use measured duration, including uploads without stored duration metadata. Sources are limited to 16 files, 64 MiB each and 512 MiB total. Sequences have at most 16 tracks, 128 clips and one hour of content. Unknown fields fail; keyframes, transitions or foreign engine semantics are not silently discarded.

Preparation produces a content digest and summary. Explicit attachment through HTTP, MCP or CLI verifies the successful job and unchanged inputs, then appends tracks after the exact current timeline duration. The service preserves existing tracks, uses stable IDs and the shared revision-checked command transaction. A stale revision changes nothing. Successful command receipts recover lost acknowledgements; stable track/clip IDs prevent a second copy while those tracks remain present. Receipt retention follows the existing 24-hour/2,000-command policy. Removing a sequence and later attaching after receipt expiry is a new explicit insertion, not restoration of a permanent acceptance marker.

Media clips preserve source ranges, volume, mute, fades and audio role; image overlays and captions remain independently editable. Separate audio tracks allow music and speech to overlap. Visual/caption overlaps and visual gaps are rejected at preparation because the current preview has one base visual and one caption at a time. Sources and older edits remain untouched. Output size/aspect follows the existing editor export settings. This is a generic edit recipe contract, not a vid2 format importer or full native-layer round trip.

The two initial recipes are an image/title story and a video/image/music/voice/caption scene. They are ordinary forkable JSON manifests. No native rendering runtime or browser dependency is added by preparing an edit.

Empty, visible, unmuted and unlocked tracks of the matching kind are reused on acceptance, so new clips are visible in an empty editor. Existing track names, IDs and settings are retained; occupied, hidden, muted and locked tracks stay untouched. Additional tracks are appended only when needed.
