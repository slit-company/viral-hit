# 007: Browser-bound account connections

The account application service owns channel identity and encrypted credentials; the HTTP transport owns request trust, binding cookies and callback redirects. The `/connections` feature owns loading, account selection and explicit local disconnection. It does not enqueue a publication or substitute a consent success for delivery approval.

`GET/POST /api/app/publishing/accounts` enforce the shared workspace request header and Origin/Fetch-Metadata policy, with bounded strict JSON on POST. Read responses also require the header because they contain channel identities. These controls prevent cross-site browser access; they do not authenticate multiple users. This remains an operator-controlled single workspace. Network exposure requires deployment access control.

New consent requires the operator's configured callback origin to equal the request origin. The callback is never constructed from Host or forwarded headers. Each flow gets an independent 256-bit random binding in a host-only HttpOnly, SameSite=Lax cookie, scoped to the callback path and expiring after ten minutes. HTTPS adds Secure; HTTP is supported only by the existing loopback configuration rule. Cookie names derive from the state hash, so overlapping tabs do not overwrite each other's bindings. Missing, duplicate and wrong bindings reject before flow consumption.

The callback is the deliberate cross-site GET exception. It checks configured origin, state and the initiating cookie, then delegates one-time consumption, PKCE exchange, scope checks and channel verification to the service. Its empty 303 response sets no-store/no-referrer and a restrictive CSP, expires only its own cookie and redirects to a fixed local page containing a bounded result code. Raw codes, state, provider descriptions and caller-controlled return URLs never appear in that page. No scripts, third-party resources or token-bearing HTML are served by the callback.

Read/disconnect operations open local account management independently of Google configuration, so missing settings cannot trap stored credentials. Disconnect uses the account revision and fences ongoing reconnections through the existing store. Stale cards must refresh instead of overwriting newer state. Tokens, ciphertext, PKCE verifiers and private flow data never enter public responses.

Verification combines Request/Response tests through real OAuth/account application services with fixture network responses, and actual browser navigation to an intercepted consent document followed by a real denied callback. This establishes transport/cookie/UI behavior without claiming live Google consent, permissions or publication. Sources: [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [browser cookie attributes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
