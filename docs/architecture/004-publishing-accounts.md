# 004: Workspace publishing accounts with isolated credentials

Status: server service and browser account integration implemented and fixture-tested; see decision 007. No live account connected by this work.

`core/publishing/` owns workspace account identity, OAuth attempts, credential storage and token refresh. Publication intents retain their explicit account/destination IDs. Connecting an account does not approve or enqueue a publication. Generic execution continues to resolve credentials server-side, and the YouTube transport checks the exact credential against the intended channel before session creation.

Use `oauth4webapi` 3.8.8 for protocol request/response validation, PKCE and refresh processing. The package has no runtime dependencies and a registry unpacked size of 326,361 bytes at inspection. Import it only from server modules. Fixed Google authorization/token endpoints avoid accepting caller-controlled token destinations or discovery URLs. Bound network deadlines and response bodies, disable redirects and do not expose raw library errors containing token responses. Protocol-library use does not substitute for application state, scope or account checks.

OAuth configuration is operator-owned client ID/secret and one explicit callback URL, never inferred from request Host headers. HTTPS callbacks are required except loopback development. A connection attempt persists a short-lived state hash, browser-binding hash, PKCE verifier and intended client/account identity before redirecting. Callback consumption is atomic and one-time, requires the initiating browser binding, and rejects stale/configuration-mismatched attempts. Reconnecting an existing account must preserve its verified YouTube channel; connecting another channel creates another account ID.

Credentials are encrypted with Node AES-256-GCM and account-specific associated data. A separate private 32-byte workspace key is created atomically, or supplied explicitly by the operator. SQLite and key files are private regular files. This prevents a database-only copy or accidental record swap from revealing/reassigning tokens; it does not isolate credentials from an administrator with the key and database. A missing/invalid existing key must fail closed, never silently rotate and discard credentials.

Refresh operates outside SQLite transactions under a process-safe lease and revision/token compare-and-swap. Disconnect fences stale refresh/callback writers immediately. Expired or revoked grants become reconnect-required; transient network errors retain the original encrypted grant and back off. Requests for an old account/client/destination identity cannot silently switch to another account. Browser/API account views expose only safe account/channel/status/revision fields, never ciphertext, tokens, PKCE verifiers or session URLs.

Tests cover state replay/mix-up rejection, browser binding, denied/partial consent, identity mismatch, bounded responses, encryption/context binding, restart recovery, concurrent refresh and disconnect races. HTTP trust handling, browser-binding cookies and account UI are implemented in decision 007. Publication approval and scheduling integration remain open. Live Google consent and publication are separate user-authorized verification steps. Sources: [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [YouTube authorization](https://developers.google.com/youtube/data/guides/auth/server-side-web-apps), [oauth4webapi](https://github.com/panva/oauth4webapi).
