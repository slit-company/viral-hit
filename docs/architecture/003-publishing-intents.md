# 003: Publishing is a durable, approved export operation

Status: transport and durable executor implemented; application integration in progress.

`core/publishing/` owns account/destination identity, immutable exported-media identity, metadata, approval, upload progress and remote receipts. It does not own generation or analytics. UI/HTTP/MCP must call the same application service. Transport implementations are server-only, use bounded streaming/chunks and add no browser SDK dependency.

A publication intent binds project/export asset ID, byte size/SHA-256, destination/account, metadata, notification/privacy/scheduling choices and approval revision. Editing any of these invalidates approval. Credentials are resolved server-side; access tokens and resumable-session URLs must not appear in browser catalogs, public job projections or ordinary logs. Approval permits only that frozen intent, not an arbitrary future export.

Persist an initiating intent before a remote session request, and persist its returned session URL before sending media bytes. A missing acknowledgement or failed local receipt write is not evidence that the remote operation failed. Resume from provider-reported byte progress; never infer it from bytes written to a socket. A completed upload is distinct from video processing, scheduled release and public visibility. Expired sessions or lost session-creation replies require reconciliation/manual resolution, not automatic creation of another public object.

The SQLite store uses revision/digest approval, project-scoped idempotency, 120-second fenced leases and transition events. Each executor step has a 55-second cancellation signal, commits `starting` before session creation, and commits its private checkpoint before the next step may send bytes. Expired `starting` remains uncertain. Local stop fences the old writer while retaining its lease deadline to quarantine in-flight requests. Reconciliation only reads the original session/receipt; resuming an incomplete upload is a separate operation. Repeated unchanged polls update one row without adding idle events. Runtime boundaries must honor cancellation and verify approved media integrity; the executor alone does not supply storage or credentials.

YouTube transport verifies the OAuth channel before session creation, explicitly sends privacy/children/synthetic-content/subscriber-notification choices, validates the returned Google upload URL, disables redirects and caps JSON responses. It sends bounded chunks and queries an existing session before each transfer. Account/receipt mismatches remain unknown outcomes. The connector separates accepted bytes, processing, processed private/unlisted media, scheduled private media and confirmed public visibility. A past scheduled time is never interpreted as proof of publication. Project-owned media pinning/streaming is implemented below. Provider credentials and browser account connection are implemented in decisions 004 and 007. Publication approval UI/HTTP/MCP, worker scheduling and live publication verification remain required before exposing publishing as an operational feature.

Verification starts with official-protocol fixtures and actual local HTTP byte transfer, including partial acknowledgements, lost final replies, expired sessions, wrong channels, unsupported redirects and bounded responses. Those tests do not prove a real YouTube upload. Meta/Instagram connectors will share the intent/receipt boundary while retaining their own remote creation/publish stages.

## Retained project media

The publishing domain owns a private retained copy of selected project media. Preparation accepts project-owned asset IDs at the application boundary, verifies the local source against its recorded size/SHA-256 while copying in fixed 8 MiB blocks, then commits a content-addressed file and a SQLite manifest. No complete export is loaded into memory. The manifest binds project, asset, content type, full hash and per-block hashes. Files must be durable before their manifest is committed; interrupted preparation may leave unreferenced files, never a ready manifest pointing at a partially written file. A repeated preparation must verify an existing file rather than overwrite it silently.

Approved intents refer to the retained asset identity. Source edits/deletion cannot change those approved bytes. Reads are capped at 8 MiB and verify every touched block against the private manifest, including unaligned ranges after partial remote acknowledgements. The pre-session check validates snapshot identity/availability; each transfer verifies its bytes before sending. This avoids repeatedly hashing an entire large export during every short worker lease. Storage corruption can stop a transfer after a session exists but cannot authorize substituting different bytes. This is local integrity enforcement, not protection against a malicious administrator who can modify both the private database and files.

Snapshot storage has no network dependencies and is shared by all publishing connectors. Credential resolution, UI/MCP/HTTP validation and scheduling remain separate responsibilities. Retention/garbage collection needs an explicit later policy tied to live publication references; do not automatically delete an original session's only recovery media.
